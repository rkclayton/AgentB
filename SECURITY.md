# Security

Agent_b executes shell commands selected by a model. Use it only where that authority is acceptable.

## Workspace and shell boundary

With the service identity disabled, the workspace remains the boundary for built-in file tools solely because `internal/tools/jail.go` constrains their paths; that guard is not a security boundary and must not be removed. With the service identity enabled, those file tools impersonate the configured low-privilege Windows account and accept absolute paths; Windows ACLs then decide which paths they can read or modify. The `shell` tool is not jailed and never has been: the workspace is only its initial working directory, and it can change directories, use absolute paths, invoke network clients, and run any program available to its active token. Service-account ACLs constrain what shell can reach, not what it can do with reachable resources. The wrapper kills the process tree on timeout, checks a small configurable denylist, and logs the complete call and result. [Windows host hardening](docs/HARDENING.md) reduces blast radius; it is not an OS sandbox.

The default file-routing guard refuses simple shell shapes that duplicate `find_files` or `read_file`. It is a routing aid, not a security boundary: it does not restrict what the shell can do and is not a sandbox. `tools.find_files.skip_roots` avoids recursively enumerating known protected Windows and Defender trees under either identity; it is behavioral hygiene, not access control, and Windows ACLs remain authoritative.

Agent_b never launches PowerShell with an execution-policy bypass and rejects a model command that proposes one before creating a process. Shell rejects commands that write Windows script-host artifacts and refuses to execute an agent-written `.ps1`/`.psm1`/`.bat`/`.cmd`/`.vbs`/`.wsf`/`.hta` through PowerShell, pwsh, cmd, wscript, cscript, or mshta. Python, Node, Go, .NET, and other interpreters are deliberately outside that narrow provenance rule. Multi-line PowerShell uses `run_script`, which passes source on stdin with `-NoProfile -NonInteractive -Command -` and never uses `-File` or `-EncodedCommand`. These are process-tree hygiene controls, not containment; a shell remains capable within the permissions of its active Windows token.

Code-signing commands (`Set-AuthenticodeSignature`, `signtool`, and `certutil` store operations) are blocked from `shell` and `run_script` under every identity. Signing is available only through Settings and is guarded by the verified operator HTTP-process check. Create uses UAC to place a non-exportable key in `LocalMachine\My`; its default machine-key ACL limits private-key use to elevated administrators/SYSTEM, while only its public certificate is trusted in the operator's CurrentUser TrustedPublisher and Root stores. This makes upgrades silent inside the already-elevated installer without giving non-elevated operator mode or `agentb-svc` the signing key. Import places a code-signing-EKU certificate in `CurrentUser\My`, uses the PFX password once, does not alter trust stores, and retains the organization's key-protection policy. The elevated signing helper accepts no filesystem paths, derives roots from the verified running process, compares the executable SHA-256 shown by `/api/state`, stages and verifies signatures before replacement, and restarts with the operator's limited token. `signing.applied` is the durable audit record after restart.

The non-elevated-operator side of that signing boundary was checked directly on 2026-09-06: a medium-integrity Explorer-token child could not sign with LocalMachine certificate `8C7AB22A989F6B99B867868A52920119C3EDFFEB` (`result=DENIED`), as recorded in `%LocalAppData%\Agent_b\logs\main-20260906T123516.jsonl` and `NOTES.md`.

Model-profile API keys are not stored in `harness.json`. A profile keeps a lowercase credential reference; the corresponding value is protected with Windows DPAPI under the launching user's scope and decrypted into the in-memory profile when configuration loads. Masked API responses and configuration events expose only `•••• set`, and request/event logs do not contain the key. The existing service-account password remains in its separate fixed DPAPI store.

The first-run wizard is sequencing over the existing configuration, credential, probe, and session interfaces; it adds no persistent completion state and does not change probe semantics. Its local detector is read-only: it queries Windows hardware/process information and known executable locations, does not alter `PATH`, install software, download models, or start servers. An interpreter's `runs as service` label means the configured service account (or a broad built-in group it belongs to) has read/execute ACL entries on the resolved executable; `operator-only` means that check found no such grant. This display is an onboarding hint, not a security boundary or a proof that every dependency is reachable. Windows ACLs remain authoritative at execution time.

The Settings → Security control labeled **Run everything as me for 20 minutes** is an explicit, process-global capability escape hatch. It bypasses service-account isolation for shell and file tools, including the file tools' workspace boundary, and leaves access decisions to the non-elevated Windows account that launched Agent_b. Switching modes is immediate and does not open a confirmation dialog. While active, every Chat status strip shows `operator mode · until HH:MM`; Settings shows the high-contrast active robot glyph and both surfaces return to off state from authoritative server events when a grant fails or expires. Operator-mode transitions are status, not agent-authored chat messages. Each SSE connection and foreground resume reconciles server state so a suspended or disconnected client cannot retain a stale privilege indication when it resumes. Operator mode is always off after startup and process exit. It has no absolute ceiling while active work continues: by default it turns off after 20 minutes without ordinary agent tool execution, and every such execution resets the deadline at start and completion. Browser/SSE/config reads and the one-shot ACL escape do not reset it. A single tool call running longer than the window is deliberately allowed to lapse rather than risk an indefinitely open grant behind a wedged call. Every transition, reset, and operator-context tool result is logged. Enabling, disabling, or changing the service-identity configuration through HTTP requires the request's local client process to belong to the Agent_b operator and rejects Agent_b itself or any descendant process; possession of the browser mutation token alone is insufficient, so neither a service-account shell nor an operator-context shell can change the mode or disable the split. This does not grant Administrator authority, bypass Windows ACLs, or create a sandbox.

In service-identity and operator-context modes, built-in file tools deliberately let Windows ACLs authorize paths and do not pre-resolve symlinks or open every ancestor for metadata inspection. This widened resolution at `ce73fc0`: ACL-authorized targets beneath traversable but metadata-inaccessible parent directories, and OS-authorized symlink paths, can now reach the underlying file operation where previously the metadata check could reject them first. The ordinary workspace-bound mode still canonicalizes symlinks and rejects escapes; in OS-authorized modes the Windows token is the intended boundary.

When `shell.service_account.enabled` is false, the shell inherits the Agent_b process identity and environment as before. When it is true and the stored credential works, Agent_b creates shell processes under the configured low-privilege Windows identity with an explicit minimal environment. Its `PATH` contains only Windows system directories and the Windows PowerShell directory, so other tools require absolute paths. A failed alternate-identity launch does not execute the command: it logs the reason, raises persistent red status text in the header, and requires the user to approve an exact-command operator retry. The alternate path preserves the initial working directory, combined output, timeout, and process-tree termination through a Windows job object, but it still requires an operator-machine test before being relied upon. A separate account limits reach; it is not a sandbox and does not contain an exploit. Follow [Windows host hardening](docs/HARDENING.md) before relying on the split.

On Windows, the normal service-context process tree is `Agent_b.exe → powershell.exe → any program named by the inline command`. `CreateProcessWithLogonW` creates PowerShell directly as the service identity; there is no intermediate `cmd.exe` or generated script. `fetch_url` performs anonymous, governed open-web HTTP inside `Agent_b.exe`; it neither downloads through PowerShell nor hands fetched bytes to the service shell. `call_service` is deliberately separate: it reaches only configured internal-service base URLs, attaches only the configured service identity, and runs an `exec:` credential argv directly as the non-elevated operator with no shell. Its bearer value remains in process memory, model-supplied authorization values are redacted from durable/UI projections, and any reflected token is scrubbed from the returned body. A configured service is an explicit authority grant, not an extension of the public-web fetch policy.

Settings can launch the account setup script as a hidden elevated helper through Windows UAC while Agent_b remains non-elevated. The two password entries are write-only, are never placed on a command line or in logs, and cross the elevation boundary only as the existing user-scoped DPAPI blob. Keep the service on loopback, approve UAC only for an operation you initiated, and treat any failure after the elevated helper starts as a potentially partial account/password change.

Agent_b refuses to start when its effective Windows token is elevated, before loading configuration, probing a model, opening the listener, or enabling shell execution. Membership in the local Administrators group is allowed: a normal Explorer launch uses the UAC-filtered token. This keeps **Run once as operator** from inheriting Administrator authority.

The model prompt receives only OS-derived date, timezone, and (on Windows) a coarse region code. Agent_b does not collect precise device location or infer a city from that context; this information is convenience context, not a location-tracking feature.

Settings can also apply and verify complete-tree service-account ACLs and a single account-scoped outbound Block rule through UAC. The ACL policy grants mutation only on the configured workspace and exchange folder and must be reapplied after application updates create or replace files. The firewall policy permits loopback and the complete Tailscale carrier range; it does not change machine-wide firewall defaults or inspect destinations above the IP layer.

Chat file downloads are read-only operations performed by the Agent_b server process as the non-elevated operator. They expose only regular files that the shared file-tool jail resolves beneath the selected session workspace; this jail remains an application guard, not containment. The open-folder action is mutation-token protected and resolves its selection through the same jail before asking the operator desktop to reveal it.

The exchange folder is a fourth, explicitly configured reachable tree, separate from application, operator data, and workspace roots. Host protection grants the service identity recursive `Modify` on that folder and only traverse access on otherwise private ancestors needed to reach it. This intentionally widens the OS boundary to the exchange folder so files placed there can later enter the attachment workflow; changing the folder requires reapplying and verifying host protection. Network shares, mapped drives, and SMB credentials are not supported.

Attachment ingest is an operator browser action protected by the launch mutation token, not a model tool or approval escape. The operator-context HTTP process writes at most `tools.attachments.max_bytes` beneath the selected session workspace's `attachments/` directory through the shared file-tool resolver; the service identity subsequently reads those bytes under the workspace ACL. Filenames are reduced to safe basenames, ZIP archives are refused, collisions never overwrite, and JSONL records contain only path, size, and SHA-256—not attachment bytes. Native document/image bytes exist only in the in-memory model request. Configured extraction endpoints receive the uploaded file and their text sidecars are explicitly labeled untrusted; Office XML extraction is bounded and uses the standard library without extracting archive paths.

The Windows installer uses same-user UAC elevation to place immutable application files under `%ProgramFiles%\Agent_b`; it refuses elevation performed with another administrator identity so `%LocalAppData%` and user-scoped DPAPI cannot silently bind to the wrong profile. Configuration, credentials, logs, and memory remain operator-owned under `%LocalAppData%\Agent_b`, while the service workspace is isolated under `%ProgramData%\Agent_b\workspace`. An unsigned Agent_b binary in a user-writable AppData installation was quarantined once as a behavioral detection. Program Files is therefore required both to remove that risk factor and to prevent the constrained service identity from modifying the binary that constrains it; code signing remains separate work and no Defender exclusion is requested. The uninstaller can preserve or purge the two data roots, but it does not silently delete the service account, ACL policy, or firewall rule because those machine-level controls may be shared.

## Approval and unattended runs

Agent_b has two user-facing prompts. **Allow this** governs a risky action under `approval.mode` or a trusted repository policy: the shipped `boundary-only` default runs tools without generic pre-execution confirmation, `mutating` pauses `write_file`, `edit_file`, `shell`, and `run_script`, and `all` pauses every tool call. **Run as you** governs every need for the operator's Windows identity: configured operator commands, built-in file operations outside the service account's reach, and operator-only interpreters. Its buttons are **Yes, for this chat**, **Just once**, and **No**. One chat grant covers all those identity needs until `session.closed` or explicit revocation; it is durable, never global, and is not a separate shell/file permission. The Settings operator mode is the distinct process-global control and is never implied by a chat grant. If the service identity is disabled, there is no identity gate because the operator is already driving an unrestricted shell. Approval reduces accidental actions; it does not turn the shell wrapper into a sandbox.

When Windows denies a built-in file operation, shell output looks like an OS permission denial, or a requested interpreter exists only for the operator, Agent_b raises **Run as you** in every approval mode. **Just once** reruns only the displayed operation; **Yes, for this chat** sends later file, shell, and interpreter identity needs through the same non-elevated operator identity until the chat closes or the status-strip robot is used to revoke it. The model cannot invoke the operator path directly, the UI shows the exact path or command, and each decision, grant, lapse, and revocation is logged. File-tool denial comes from the impersonated Windows token; shell denial classification remains a text heuristic. Inspect the operation before approving: this escape deliberately bypasses service-account ACL and firewall restrictions and is not a security boundary.

## Network exposure

Agent_b has no user authentication and ships with `listen` bound to loopback. Each launch generates an unguessable mutation token delivered through the same-origin state stream; every non-read request requires that token, cross-origin browser mutations are rejected, framing is denied, and a restrictive Content Security Policy is sent. This is a browser/CSRF barrier, not authentication against another process running as the operator. Moving the listener off loopback exposes an endpoint that can run shell commands and requires a real TLS/authentication design.

The `fetch_url` tool is the governed public-network path. It performs GET-only, cookie-free requests with no model-supplied headers, rechecks every redirect and resolved address, denies loopback/private/link-local destinations unless the exact host is configured in `tools.fetch.allow_internal_hosts`, caps time and bytes, refuses binary content, and labels the returned text as untrusted in both model context and the timeline. Its browser-shaped TLS ClientHello improves compatibility; it does not impersonate a signed-in browser or make fetched instructions trustworthy. DNS/IP validation and domain allowlists reduce SSRF exposure but are application guards, not a network sandbox; `tools.fetch.allow_domains` is empty for first-run usability, but an explicit allowlist is recommended for untrusted workloads. With no allowlist, `tools.fetch.deny_domains` blocks known IP-geolocation hosts before DNS or request dispatch; an explicit allowlist supersedes this default guard. The system prompt separately forbids using network tools to discover the operator's location, identity, or IP. On a hardened Windows host, the service-account firewall blocks public network access from `shell`; `fetch_url` runs in the Agent_b process and is therefore the only sanctioned service-context path. Operator mode deliberately removes that firewall enforcement, and an unhardened host may let shell clients reach the network.

## Stored model content

`logs/*.jsonl` contains complete prompts and responses, including file contents and command output, and is ignored for that reason.

`memory/*.md` contains model-authored notes that are injected into future sessions' system prompts for the same workspace. The `remember` and `recall` tools deliberately run as the Agent_b application identity rather than through the service-account `FileIdentity` wrapper. This is a narrow exception: neither tool accepts a path, filename, workspace, or routing argument; the application derives the one reachable file from the operator-configured memory directory and the active session workspace. The model supplies only note content to `remember`, while `recall` is read-only. Operator mode does not widen either tool. Running these tools through the service identity would also conflict with the hardened installation's deliberate write denial on the memory directory.

Each chat binds one canonical workspace directory; the built-in file tools keep that directory as their jail root even while impersonating the service account, and only the existing explicit operator-decision path may leave it. Repository `AGENTS.md`/`CLAUDE.md` text is prompt content, never executable policy. A root `.agentb/policy.json` is honored only after the operator approves its exact SHA-256, which is stored under the operator-owned data/memory root rather than in the repository; model file tools refuse writes beneath `.agentb/` under the named repo-policy immutability rule. Repository policy may loosen listed session defaults, but it can never control this list: **operator mode, elevation, signing, allow_internal_hosts, services allowlist**. Windows ACLs and the service account remain the security boundary; the workspace resolver is an ergonomic guard, not containment.

A note derived from untrusted content can persist across sessions. Review it—the settings sheet shows the content and `recall` returns the dated stored entries—and remove the note file manually if it should not be trusted or retained.

Fetched text is one such untrusted source. The envelope does not follow content into a later `remember` call automatically, so review durable notes derived from fetched material with the same care as the original page.
